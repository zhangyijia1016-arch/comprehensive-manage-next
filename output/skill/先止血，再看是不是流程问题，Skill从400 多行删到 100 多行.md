🧹 先止血，再看是不是流程问题，Skill从400 多行删到 100 多行
从单点修 Bug 到重整主流程的一次开发复盘
前段时间，我发现自己维护的一个 SKILL.md 已经写到了 400 多行。
它最开始只有 100 多行。后来每遇到一个线上问题，我就把运行记录和异常结果交给 AI，让它直接修改。
AI 的修复通常很快，也很有针对性。
输出里多了一段过程说明，就加一句“严禁输出”；模型自行补了占比，就把数字规则设为“最高优先级”；结果格式偶尔不一致，就增加固定模板；只靠 Prompt 还拦不住，再写一个 Python 脚本做最终检查。
一个 Bug 修完，文件多十几行。下次再出问题，就继续加。
十几个版本之后，主文件里已经堆满了“必须”“不得”“严禁”“未通过不得交付”。一个简单的审计发现润色，也要经过身份识别、数据检索、结构化草稿、结果渲染、脚本校验和失败重试。
规则看起来越来越严密，运行却开始变得敏感。一处修改可能影响另一段流程，为了保护刚修好的功能，还要继续补新的例外。
后来我停下来，把整个执行流程重新拆了一遍，删掉了近 300 行。
数据查询、历史口径匹配、结果润色和口径维护都还在，之前反复出现的来源丢失、流程中断和输出波动反而少了。
这次经历让我发现，让 AI 针对 Bug 改代码很容易，难的是判断这次修改应该留在主流程里，还是只做一次临时修复。


01｜每修一个 Bug，就再加一层限制
这个 Skill 的功能并不复杂：参考历史审计发现和组内口径，把用户提交的审计发现草稿改得更规范一些。
真正开始测试后，问题一个接一个出现。
有时结果前面会带出检索过程；有时用户只写了“发现 5 个问题”，模型却顺手算出了占比；材料里没有制度名称，结果中却出现了一份看起来很完整的制度；用户只要求润色，最后还附上了整改建议。还有几次，原文只是一般性描述，输出却被改成了“重大风险”或“管理混乱”。
当时的解决办法很直接：出现什么问题，就补一条对应的规则。
## 最终输出要求

- 第一行必须为 `## 一段话版`
- 标题前不得出现解释、过渡语或检索摘要
- 用户未提供占比时，不得自行计算占比
- 用户未提供制度名称时，不得新增制度名称
- 用户未要求整改建议时，不得输出建议性内容
- 不得增加用户原文中没有的风险定性
- 候选结果未通过最终校验时，不得交付

这些规则并不是凭空写出来的，每一条后面都有一个真实的 Bad Case，也确实解决过问题。
麻烦在于，AI 修改下一个 Bug 时，通常会顺着已有规则继续往下加。原来的限制不动，再补一条更具体的；担心模型不执行，就提高优先级；担心存在例外，再增加一段补充说明。
几轮下来，同一个要求可能换着说法出现好几次。原本只针对某次异常的修复，也逐渐成了所有任务都必须执行的步骤。
文件就是这样一点点长到了 400 多行。


02｜Prompt 拦不住，我又写了一个 Python 闸门
规则加到一定程度后，新的问题出现了：SKILL.md 里明明已经写了“禁止输出检索过程”“不得新增风险定性”，模型偶尔还是会漏掉。
继续加粗、提高优先级、重复强调，效果并不稳定。于是我写了一个 final_output_gate.py，在结果交付前再做一次机械检查。
它主要负责几件事：检查首行是否符合模板、必要模块是否齐全、结果中有没有残留过程性表达，以及是否新增了用户原文中没有的风险判断。
def validate_output(output: str, user_input: str) -> list[str]:
    errors = []

    if not output.startswith("## 一段话版"):
        errors.append("首行不符合输出模板")

    forbidden_phrases = [
        "根据检索结果",
        "现在开始",
        "已获取相关口径",
    ]
    for phrase in forbidden_phrases:
        if phrase in output:
            errors.append(f"存在过程性表达：{phrase}")

    risk_phrases = [
        "重大风险",
        "造成损失",
        "管理混乱",
    ]
    for phrase in risk_phrases:
        if phrase in output and phrase not in user_input:
            errors.append(f"存在定性升级：{phrase}")

    return errors

这套方式确实有用。固定标题、过程话外露、明显的风险升级，都能在最后一步被拦下来。
但运行一段时间后，我发现它管住的主要是“最后写成了什么样”，管不到“前面到底做对了没有”。
比如，脚本可以判断第一行是不是固定标题，却不知道当前用户所属小组有没有识别正确；可以检查“重大风险”是否凭空出现，却不知道检索到的历史发现是否真的相关；可以要求删除过程文字，却无法确认重新生成后，原本已经拿到的来源链接是否还在。
最后结果通过校验，只代表文本满足了几项固定条件。身份识别、数据查询、历史匹配和来源保留这些上游步骤，仍然可能出错。
也就是从这个阶段开始，我发现继续强化最终输出检查，已经解决不了整条流程里的问题。


03｜脚本通过了，结果还是会出问题
机械闸门上线后，格式类问题少了很多，但新的情况也陆续出现。

为了避免检索过程出现在正文前面，我要求所有候选结果在输出前经过脚本检查。发现问题后，脚本会把错误项交回模型，重新生成整份报告。
report = render_report(context)
errors = validate_output(report, user_input)

if errors:
    report = rewrite_report(report, errors)
过程性文字确实消失了，但重新生成整份报告时，前面已经查到的组内口径、审计发现来源和链接也可能被压缩、改写，甚至直接删掉。
于是我又补了一条规则：重新生成时必须保留来源。随后又发现，部分来源说明会被禁词规则识别成“过程话”，只能继续调整禁词范围。
一个格式问题修好后，来源展示出了问题；保护来源之后，禁词判断又要修改。每增加一层处理，都需要再补一层例外。
到这个阶段，文件变长已经不是最麻烦的事。更明显的问题是，很多规则开始互相牵制，改动一个地方，很难判断会不会影响另一段流程。


04｜先止血，再看是不是流程问题
线上出了问题，第一步当然还是先修。用户已经遇到异常时，不可能先停下来做一轮完整重构。
我后来增加的是修复后的第二步：这个 Bug 到底只是一个局部问题，还是暴露了流程设计上的漏洞。
以“历史材料被写进当前结果”为例，最开始的处理方式是增加一组禁止规则：
- 不得迁移历史金额
- 不得迁移历史部门
- 不得迁移历史人员
- 不得迁移历史风险等级
- 不得迁移历史整改状态
这些限制需要保留，但每发现一种误写内容就补一条，始终会有新的遗漏。金额拦住了，可能又带入制度名称；部门拦住了，可能又套用了历史整改结论。
后来我把问题往前移了一步，先明确不同数据源分别能做什么。
DATA_SOURCE_RULES = {
    "user_input": "当前事实来源",
    "group_convention": "组内语言偏好",
    "audit_findings": "历史表达参考",
    "knowledge_base": "无相似记录时的写法兜底",
}
后续生成时，当前问题的事实只从用户输入中提取。组内口径、历史发现和知识库继续参与润色，但只提供句式、结构和表达参考。
facts = extract_facts(user_input)

style_refs = [
    *group_conventions,
    *audit_findings,
    *knowledge_refs,
]

report = render_output(
    facts=facts,
    style_refs=style_refs,
)
这样调整后，历史材料在进入生成阶段前就已经和当前事实分开。原来的禁止规则仍然保留，用来处理异常情况，但不再承担整套防错逻辑。
这也是我后来判断是否需要重构的一个标准：如果同一类 Bug 需要不断补充新的禁止项，问题往往已经不只出在最终输出上。


05｜把一堆补丁收回主流程
重构前，SKILL.md 里混在一起的内容很多：识别用户要做什么、查询员工所属小组、读取数据表、匹配历史材料、润色正文、控制输出格式，最后还要再跑一遍脚本校验。
每个环节都有自己的规则，某一步出问题时，很容易直接在主文件里继续加说明。时间一长，主流程反而被各种例外和补丁淹没了。
我重新整理后，只保留了一条清楚的执行顺序：
识别用户意图
    ↓
识别当前用户所属小组
    ↓
检索组内口径
    ↓
检索审计发现表
    ↓
必要时查询内部知识库
    ↓
保留用户事实，生成最终结果
对应到代码里，主流程只负责调度：
def run_skill(user_input: str) -> str:
    intent = classify_intent(user_input)

    if intent == "maintain_convention":
        return maintain_group_convention(user_input)

    user_group = resolve_user_group() or "通用口径"
    facts = extract_user_facts(user_input)

    group_refs = search_group_conventions(
        group=user_group,
        keywords=facts["keywords"],
    )

    finding_refs = search_audit_findings(
        domain=facts["domain"],
        issue_type=facts["issue_type"],
    )

    knowledge_refs = []
    if not group_refs and not finding_refs:
        knowledge_refs = search_internal_knowledge(
            keywords=facts["keywords"],
        )

    return render_output(
        facts=facts,
        group_refs=group_refs,
        finding_refs=finding_refs,
        knowledge_refs=knowledge_refs,
    )
调整后，主文件只需要管几件事：先判断用户要做什么，再决定按什么顺序查询数据，区分哪些内容属于当前事实、哪些内容只能参考，最后统一生成结果。
语言风格、问题分类和反幻觉规则放回各自的参考文件；员工信息和数据表查询交给对应的下游能力；下游只返回查询结果，不再直接输出给用户。
主流程变清楚以后，原来很多反复强调的规则就可以直接删掉了。不是因为这些问题不重要，而是它们已经被放回了更合适的位置。


06｜这 300 行，主要删了什么
从 400 多行缩到 100 多行，删掉的内容大致分为几类：重复出现的过程性禁词、功能相近的输出自检、强制生成结构化草稿的中间步骤、所有任务统一经过机械闸门的要求，以及散落在多个位置的下游 Skill 调用说明。
还有一部分内容，本来已经写在风格、分类和反幻觉参考文件里，主文件中又重复写了一遍；少数规则只针对某一次异常，后续一直没有复现，也一并清理掉了。
删完之后，核心约束仍然保留：
CORE_RULES = {
    "preserve_user_facts": True,
    "allow_new_facts": False,
    "group_convention_first": True,
    "audit_findings_second": True,
    "knowledge_base_as_fallback": True,
    "traceable_sources": True,
}
用户提供的事实必须保留，未提供的信息不能补写；润色时先查组内口径，再查审计发现表，前两类来源不足时才使用内部知识库；引用过的历史材料需要能够定位；涉及组内口径写入时，仍然要先确认再执行。
最终删掉的，主要是重复表达、临时补丁和已经移到其他模块中的规则。事实边界、数据源顺序和写入控制这些关键部分，都继续留在主流程里。


07｜以后再修 Bug，我会多做一步
现在再遇到异常，我还是会先让 AI 帮忙定位代码、分析日志，尽快把问题处理掉。但临时修复完成后，我会再回头看一次：
1. 同类问题之前出现过吗？
2. 新加的规则还需要继续补例外吗？
3. 这次修改会不会影响原本正常的流程？
4. 这个问题是否同时涉及多个环节？

如果只是独立的格式异常，局部修复通常就够了。一个问题反复出现，或者每次修复都会牵出新的冲突，就需要重新检查流程顺序和模块分工。
这套判断也可以简单写成一段开发逻辑：
def choose_fix_strategy(bug) -> str:
    score = 0

    if bug.repeated:
        score += 1
    if bug.requires_exceptions:
        score += 1
    if bug.affects_other_flows:
        score += 1
    if bug.crosses_multiple_steps:
        score += 1

    return "refactor_workflow" if score >= 2 else "local_patch"
代码很简单，主要是提醒自己：一个 Bad Case 可以先修，但不一定都要写进主流程。
结语
把 SKILL.md 从 400 多行删到 100 多行后，我并没有得出“Prompt 越短越好”的结论。
事实边界、数据源顺序、写入确认，这些规则仍然需要写清楚。被删掉的，大多是重复表达、临时补丁，以及已经移到其他模块中的内容。
AI 很适合处理眼前的问题。给它一段日志和一个异常结果，它通常能很快找到相关位置，补上判断条件，给出一版可以运行的修复方案。
但一次修改要不要长期保留，新规则会不会和旧流程冲突，几个补丁能不能合并成一条更清楚的流程，这些判断仍然需要人来做。
所以现在我的处理方式是：先解决当前 Bug，再判断它是不是一个结构问题。
有时候，修好一个 Skill 最有效的动作，确实是删代码。
