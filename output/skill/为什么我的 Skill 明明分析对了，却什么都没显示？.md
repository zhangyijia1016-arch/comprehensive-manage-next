这两天在调一个面试评估 Skill，遇到一个很反直觉的问题：
模型已经分析完了，雷达图也生成了，但用户侧看到的报告是空的。
一开始我以为是 Prompt 没写清楚，于是疯狂加指令：
请完整输出
不要省略
先输出报告，再生成图表
结果改了半天，问题还在。
最后发现：
不是模型没干活，是结果在执行链路里“丢了”。

01｜工具调用，把正文“吃掉”了 🕳️
[图片]
在 dodo 环境里，如果模型先输出正文，再调用工具生成雷达图，前面的文字有概率不会保留下来。
也就是说：
模型其实分析完了，但工具调用后，正文被截断/覆盖了。
最后不是继续堆 Prompt，而是改执行顺序。
❌ 旧链路：
分析报告 → 生成雷达图 → 结束

✅ 新链路：
生成雷达图 → 输出完整报告 → 结束
这个调整很小，但很关键。
因为用户不关心模型中间有没有想明白，只关心最后能不能看到结果。
Prompt 的执行顺序，有时候比 Prompt 本身更重要。

[图片]
另一个坑是平台兼容。
同一份 Skill，在 Comate 里正常，换到龙虾或 dodo 后就可能开始“玄学报错”。
这次主要遇到这些：
坑点
表现
处理
参数截断 ✂️
长文本传参后内容丢失
拆短命令，减少一次性传参
中文符号 🈶
引号、换行、标点导致解析异常
统一清洗输入格式
Unicode 字符串 🔣
不同平台处理方式不一致
减少复杂转义，降低命令复杂度
图片展示 🖼️
图生成了，但聊天里看不到
新增 base64 输出模式
工具顺序 🔁
先文字后工具导致正文消失
改成先工具后正文
这里最麻烦的是：
很多问题在本地或某个平台看起来都没问题。
但一进入真实平台链路，就要经过：
模型输出 → 平台解析 → 工具调用 → 文件生成 → 聊天展示
任何一层处理方式不同，最后用户看到的结果都可能变样。
所以后面我尽量：
* 命令写短一点
* 参数少嵌套一点
* 输入先清洗一遍
* 关键规则放主文件
* 不把核心逻辑散到 references

原因也很简单：
模型每多读一个文件，就多一次不稳定。

03｜JD 前置：从“建议补充”改成“没有就停” 🚦
面试评估里最危险的情况，是没有 JD 还继续评估。
没有 JD 时，模型很容易自己脑补岗位标准。
比如候选人提到 SQL，模型可能直接写：
数据能力较强。
但实际要先确认：
* 这个岗位是否需要 SQL？
* SQL 是核心要求还是加分项？
* 这段经历和岗位到底有没有关系？

一开始我写的是：
如果缺少 JD，建议用户补充。
结果模型经常继续往下分析。
后来改成硬规则：
缺少 JD：
⛔ 停止分析
⛔ 不生成评分
⛔ 不生成雷达图
⛔ 不输出推进建议
✅ 先向用户索要 JD
也就是把“建议”改成“闸门”。
最后链路变成：
JD 确认
   ↓
能力维度提炼
   ↓
面试原文对照
   ↓
评分与雷达图
   ↓
推进建议
这个改完后，输出稳定很多。
有时候纯文本强制中断点，比依赖工具或 MCP 更直接。

04｜雷达图不是装饰，是岗位画像 📊
[图片]
最开始我用固定维度：
专业能力、沟通能力、学习能力、稳定性、岗位匹配度……
后来发现不够通用。
内审、技术、产品、运营，不可能都用同一套尺子。
所以后来改成：
从 JD 中动态提炼 5–8 个能力维度，再根据面试原文评分。
这样雷达图才不是“看起来好看”，而是和岗位要求绑定。
JD
↓
能力维度
↓
面试证据
↓
评分
↓
雷达图
另外还踩了一个展示坑：
图表生成成功，不代表用户能在聊天界面看到。
所以脚本也改了一版：
* 支持保存到产出目录
* 支持 base64 输出
* 尽量适配不同平台展示方式


05｜模型误判：不是不懂，是边界不清 🎯
还有一个挺有意思的问题：
模型很容易把“可培养短板”判成黄灯。
比如候选人整体匹配，面试官反馈也积极，只是某一项经验还不够完整。
模型会倾向保守，给出：
黄灯观察。
后来发现，问题不是模型没看懂，而是判断边界没有写清楚。
所以我把推进状态重新拆了一遍：
状态
判断口径
🟢 绿灯
核心能力匹配，面试官反馈积极，短板可培养
🟡 黄灯
有明显能力缺口，需要下一轮重点验证
🔴 红灯
核心要求不匹配，或风险信号明确
⚪ 灰灯
信息不足，无法判断
关键补了一句：
绿灯不等于没有短板。
真实面试里几乎没有完美候选人。
如果不把这个边界写出来，模型会默认保守。
这次也发现：
模型对格式暗示非常敏感。
同样一句规则，放在长段落里，经常被弱化；放成表格、流程块、禁止项，执行效果反而更好。

06｜description 不是广告语，是入口规则 🚪
之前我以为 description 只是展示文案。
后来发现它会影响 Skill 路由。
只写：
面试评估工具
不如写成更贴近用户真实表达的触发句：
“面试快评”
“分析今天下午的技术面”
“对比这两个候选人”
“详细分析这个面试，给下一轮面试官看”
触发句式越贴近用户表达，命中越稳定。
所以 description 不是写给人看的广告语，更像是写给系统看的入口规则。

最后一点体感 🧠
做完这版之后，最大的感受是：
稳定性优化，比加功能更花时间。
功能做出来，只是第一步。
真正耗时间的是：

✅ 不同输入下不跑偏
✅ 不同平台上不报错
✅ 调用工具后不吞字
✅ 缺少关键材料时能停住
✅ 生成图表后用户真的看得见
✅ 路由能准确命中
✅ 输出能按预期收住
所以现在再看 Skill，它已经不太像一段 Prompt。
更像一个小型工作流：
输入校验 → 任务分流 → 证据提取 → 工具调用 → 结果展示 → 自检

Prompt 只是入口。
真正决定体验的，是后面这一整条链路。⚙️
