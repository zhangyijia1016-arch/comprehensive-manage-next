2. 问题不在 Prompt，而在 Runtime
做 Skill 时很容易把链路理解成：
Prompt → Model → Answer
但实际运行更像：
Prompt → Model Reasoning → Tool Call → Runtime → Message Render → Client → User
这次问题就发生在 Tool Call → Runtime → Message Render 这一段。模型生成了正确内容，但后续工具调用改变了消息流，导致前面的文本没有稳定展示。

4. 为什么龙虾没问题，dodo 会暴露？
我的理解是，两边的 Runtime 和 Message Render 对工具调用的处理方式不一样。
层级
可能差异
Tool Runtime
工具结果是否单独挂载
Message Stream
文本流和工具调用是否共享同一消息通道
Render 逻辑
后一次工具调用是否覆盖前文
文件展示
图片 / 文件是追加展示还是重组消息
平台策略
是否保留工具调用前的文本
所以这不是单纯的 Prompt Bug，而是平台兼容问题。尤其涉及图片生成、文件上传、报告保存、状态更新时，一个平台跑通不代表另一个平台稳定。

6. 修复方案：Atomic Output
这次最终引入了一条规则：Atomic Output（原子性输出）。
核心原则：
输出开始以后，不再调用任何工具。
修复前：
生成雷达图
  ↓
输出报告
  ↓
Write 保存
  ↓
BOS 上传
  ↓
TodoWrite 更新状态
修复后：
生成雷达图
  ↓
BOS 上传
  ↓
TodoWrite / memory 等状态操作
  ↓
确认所有工具调用完成
  ↓
输出完整报告
  ↓
结束回合
一句话概括：
先干活，再说话；说话开始后，不再干活。

7. Skill 里的具体改法
这次补的是硬规则，不是软提示。
步骤5：完成所有需工具调用的前置操作

- 生成雷达图
- 上传雷达图到 BOS
- 完成 TodoWrite 状态更新
- 完成 memory 操作
- 完成其他所有工具调用
- 确认后续不再需要任何工具调用

步骤6：输出完整评估报告【Atomic Output】

- 所有工具调用完毕后，开始输出文字
- 输出期间禁止调用任何工具
- 禁止 Write / Bash / Edit / TodoWrite / memory
- 禁止一边输出报告一边写文件
- 禁止一边输出报告一边上传文件
- 报告只以对话框纯文字形式输出

步骤7：报告末尾输出提醒框

步骤8：结束回合

- 报告输出后不得再执行任何工具调用
- 如需保存报告，等用户下一轮回复“保存”后再执行
